# 定时与邮件：从「可配置」到实际生效

**当前仓库没有运行中的调度器、SMTP 服务或托管后端。** 它提供内容与陪伴规则，以及供宿主在用户授权后执行的 [定时与投递流程](../skills/sidequest/assets/delivery.md)。这里的例子不代表已经创建任务或发送邮件。

## 三部分都要接上

| 部分 | 负责什么 | 必须实际确认的条件 |
| --- | --- | --- |
| 个人 Skill | 选内容、控制总量、按反馈调整 | 每次运行能读取同一份已确认方案 |
| 定时工具 | 到点运行 | 时区、频率、设备在线要求、运行限制 |
| 消息或邮件工具 | 把正文送到指定位置 | 支持完整正文、正确收件人、发送权限与费用 |

通知里有一个链接，不等于完整内容已经发进邮箱；可以发邮件，不等于可以读回复。不要要求用户把密码、邮箱授权码或 API 密钥写进 Skill。

## 可直接交给助手的配置请求

```text
请先检查当前环境能否定时运行，以及能否发送完整邮件正文。
使用我已确认的个人 Skill，不增加原方案的每周次数或时间预算。
我希望在约定的时区、时间收到一小份内容；先和我确认具体频率、
收件地址、内容范围、运行条件和停止方法，再创建或更新任务。
请先展示一份邮件预览。测试发送需单独问我；没有相应能力就说明。
不要把我的完整画像、聊天记录或私人经历写进任务正文或邮件。
```

例如选择 `Asia/Shanghai`、每天 08:30，也需要先让用户确认：这是否符合原本每周的支线预算？不能把每周两次悄悄升级成每天一次。

## 推荐的实际接通步骤

1. 检查当前宿主已有调度与发送工具，不安装未经确认的服务。
2. 确认个人目录、时区/频率/时间、接收位置与内容边界；检查已有同类任务。
3. 展示一份预览，让用户确认内容像自己的支线，而不是通用资讯。
4. 获得授权后创建/更新任务，记录实际任务标识；若允许，再测试发送。
5. 分别交代：任务是否创建、发送接口是否成功、用户是否确认收到，以及如何暂停。

自动运行失败不等于用户没坚持；发送结果不明时先查状态，不反复重发。日志不得把「已发送」记成「已学会」。默认不补发错过的多份内容。

## 一封支线来信示例

以下是虚构的五分钟体验，不是自动发送记录：

> **今天的支线｜收集一束光**
>
> 先不学术语。找一个手边的小物件，给它拍两张不同角度的照片。
> 看一眼阴影有什么变化，挑一张你更喜欢的就好。
>
> 没有自然光，就用现有台灯。不想拍，也可以只观察或休息。
> 下次回到对话，告诉我你喜欢哪里，我们再接着走。

未接通回复处理时，让用户回到原对话反馈。接通邮箱读取是额外能力与权限，不因设置发送而默认开启。

## 暂停与隐私

明确说「暂停我的人生支线推送」，并核对关联任务的暂停结果。如果助手无法修改该任务，需要到原调度工具停止；退出聊天本身通常不等于取消已建立的任务。

个人目录不应提交到公共仓库。`.gitignore` 只是降低误提交风险，不能保护已经上传过的文件。不要将真实收件地址、凭据、私人画像或发送日志作为示例提交。
